# Vulnerability-Hunting Pass — Findings

Hunting pass run against `audit-context/DOSSIER.md` and its 13 per-function analyses under
`audit-context/functions/`. Like the dossier, this pass was built independently of the prior manual audit
reports in `audits/` (pashov, ethskills) — any overlap with those is coincidental convergence from reading the
same code, not cross-referencing. All five findings below were independently confirmed by direct source
reading (grep + full read of the relevant functions and, where noted, the deploy script) during this pass.

Scope: `src/NFTVoting.sol`, `src/base/{INFTVoting,Proposal,Settings,Votes}.sol`, `src/erc721/GovernanceERC721.sol`.

Ranked most severe first.

---

## [FIXED] 1. `execute(uint256)` has no access control — `EXECUTE_PROPOSAL_PERMISSION_ID` is dead code

**File:** `src/base/Proposal.sol:43` · **Category:** access-control · **Verdict:** CONFIRMED

The public `execute(uint256)` function carries no `auth(...)` modifier or any other access check — its only
gates are `_canExecute()` and a nonzero-voting-power check on `_msgSender()` (Proposal.sol:47-52). Meanwhile
`EXECUTE_PROPOSAL_PERMISSION_ID` (declared at `Proposal.sol:27`) is never referenced by any modifier or
explicit check anywhere in `src/`, `script/`, or `test/` — confirmed by repo-wide grep. The deploy script
(`script/InstallNFTVoting.s.sol`) never even grants it to anyone (only `CREATE_PROPOSAL_PERMISSION_ID` is
granted, to `ANY_ADDR`, at line 200).

**Failure scenario:** A DAO operator believes execution rights are controllable through the DAO's permission
manager — why else would the permission ID exist, alongside `CREATE_PROPOSAL_PERMISSION_ID` and
`UPDATE_VOTING_SETTINGS_PERMISSION_ID`, which genuinely gate their functions — and never grants
`EXECUTE_PROPOSAL_PERMISSION_ID` to anyone, expecting execution to be restricted. In fact any address,
permissioned or not, can call `execute()` the instant `_canExecute()` returns true, giving an unaffiliated,
unstaked caller unilateral choice of the exact block a passed proposal executes in (MEV/sandwich exposure for
any action whose outcome depends on external state), with no configuration path available to prevent it.

**Resolution:** `EXECUTE_PROPOSAL_PERMISSION_ID` and `CREATE_PROPOSAL_PERMISSION_ID` with its respective `auth()` functions have been removed from the codebase. `canCreateProposal` and `canExecuteProposal` already check if the sender has sufficient voting power to execute the function

## [WONT-FIX] 2. `maxBoundDate` has no upper bound, unlike every sibling ratio field

**File:** `src/base/Settings.sol:136` · **Category:** input-validation · **Verdict:** CONFIRMED

`_updateVotingSettings` bounds `supportThreshold`, `minParticipation`, and `minApprovals` to hard ceilings
(999,999 / 900,000 / 900,000) but places no upper bound on `maxBoundDate` — only `maxBoundDate >= minDuration`
is checked (`Settings.sol:136-138`). `maxBoundDate` is then reused *additively* in `_validateProposalDates` to
bound both how far in the future `startDate` may be set (`Proposal.sol:405-407`) and, independently, how long
the voting window may run (`Proposal.sol:425-429`) — so the worst-case `endDate` reaches
`currentTimestamp + 2*maxBoundDate` with no contract-level ceiling at all. The 365-day figure in
`script/InstallNFTVoting.s.sol:269` (`vm.envOr("MAX_BOUND_DATE", 365 days)`) is only a deploy-script default,
fully overridable via `.env`, not an on-chain guard.

**Failure scenario:** DAO governance (auth-gated, but reachable through the plugin's own proposal mechanism)
or a misconfigured deployment sets `maxBoundDate` to an extreme value (e.g. decades). Since
`CREATE_PROPOSAL_PERMISSION_ID` is granted to `ANY_ADDR` in the install script
(`script/InstallNFTVoting.s.sol:200`), any address can then create a proposal pinned to today's snapshot but
dated to open and close years from now, deciding a matter with a long-stale electorate by the time anyone can
vote on it.

**Resolution:** worth considering this possible scenario but not enough to hard code magic numbers in the smart contracts themselves. `maxBoundDate` already works as a bound for other values. If we go down the rabbit hole of adding upper bounds to bounds we might end up in a infinite loop of bounds of bounds.

## [WONT-FIX] 3. Succeeded proposals never expire after `endDate`

**File:** `src/base/Proposal.sol:91` · **Category:** correctness · **Verdict:** CONFIRMED

`_canExecute` (and its callee `_hasSucceeded`) place no upper time bound on how long after `endDate` a
proposal that reached its thresholds remains executable — once `_hasSucceeded` returns true for a closed
proposal, it stays executable indefinitely, since nothing in the function ever compares the current time
against `endDate` on the success path.

**Failure scenario:** Combined with Finding 1's permissionless `execute()`: a proposal passes, but execution
is deliberately withheld by whoever intends to call it. That party can later execute the exact same approved
actions at a time of their own choosing — months or years after the vote concluded, against conditions the
electorate never evaluated and with no mechanism for the DAO to invalidate a stale-but-approved proposal.

**Resolution:** This behaviour is intended in order to show the permissionless feature of a public sector DAO. The approved proposal will be able to be executed no matter what (including time). It is important that off-chain actors monitoring approved proposals to execute them in a timely manner.

## [] 4. `minProposerVotingPower`'s upper-bound check is skipped on the very first `initialize()` call

**File:** `src/base/Settings.sol:147` · **Category:** input-validation · **Verdict:** CONFIRMED

The check bounding `minProposerVotingPower` against current total voting power (`Settings.sol:155-159`) is
gated by `votingSettings.maxBoundDate != 0` — a value that is unconditionally zero the first time
`_updateVotingSettings` runs, i.e. during `NFTVoting.initialize` (`src/NFTVoting.sol:49`, called before
`votingToken` is even set at line 50). So the one safety check that exists for this field never applies at the
one moment (genesis) a deployer-supplied value is least likely to have been sanity-checked externally.

**Failure scenario:** A deployment script or manual deploy call passes an oversized `minProposerVotingPower`
(e.g. a units mistake). The check that would normally reject it is structurally skipped, permanently disabling
`createProposal` for every account from block zero — and because fixing it requires a passing proposal through
this same plugin, there is no in-contract recovery path.

## [WONT-FIX] 5. A third party can silently reverse a holder's `delegate(0)` opt-out

**File:** `src/erc721/GovernanceERC721.sol:169` · **Category:** correctness · **Verdict:** CONFIRMED

`_afterTokenTransfer`'s auto-self-delegation fires whenever `delegates(to) == address(0)`, but OpenZeppelin's
`VotesUpgradeable` storage cannot distinguish "never delegated" from an explicit `delegate(address(0))`
opt-out — both read as the same zero value. Any ordinary, receiver-consent-free ERC-721 transfer
(`transferFrom`/`safeTransferFrom`) that lands a new token on an address re-triggers self-delegation for that
address.

**Failure scenario:** Holder H calls `delegate(address(0))` intending to permanently abstain from wielding
voting power. A third party who owns any token calls `transferFrom(self, H, tokenId)` — no cooperation or
approval from H required — which silently re-arms H's voting power by self-delegating H again, reversing H's
expressed choice without H's knowledge.

**Resolution:** users can simply abstain from voting. It does not matter that the token is delegated to themselves. If the token was transfered to their address, they could burn them later by sending the tokens to the zero address.

---

## Cross-cutting note

Findings 1–3 form a cluster, not three independent issues: permissionless execution (1) + no execution-window
expiry (3) means a passed proposal is a standing, indefinitely-exercisable option for whoever chooses to hold
it, and the missing bound on `maxBoundDate` (2) means the proposal that produced that option can itself have
been decided by a badly stale electorate. Worth the team's attention as one design question — "who controls
*when* and *by whom* an approved decision gets carried out" — rather than three separate line-item fixes.
