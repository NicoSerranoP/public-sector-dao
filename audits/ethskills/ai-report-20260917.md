# Security Audit Report — NFTVoting (Aragon OSx Plugin) & GovernanceERC721

**Repository**: NicoSerranoP/token-voting-plugin (fork of aragon/token-voting-plugin)
**Scope**: `src/NFTVoting.sol`, `src/base/{INFTVoting,Proposal,Settings,Votes}.sol`, `src/erc721/GovernanceERC721.sol`, `script/InstallNFTVoting.s.sol`, `.env.example`, `README.md`
**Method**: 8 parallel specialist passes (general, precision-math, governance, access-control, ERC-721, proxies, DoS/griefing, signatures) against domain checklists, each independently verifying claims against library source (`lib/osx`, `lib/osx-commons`, `lib/openzeppelin-contracts-upgradeable`) and, where applicable, backing findings with compiled/passing Foundry PoCs.
**Context**: git history shows 5 recent fixes already applied (early-execution-before-endDate logic, initializer disabling order, 365-day duration bound, `_msgSender()` in proposal-id, clock detection) — all verified complete and not re-reported except where noted as incomplete.
**Full detail**: each specialist pass's complete checklist walkthrough, PoC code, and "reviewed but not applicable" notes are preserved in [`findings/`](./findings/) (`general.md`, `precision-math.md`, `governance.md`, `access-control.md`, `erc721.md`, `proxies.md`, `dos.md`, `signatures.md`). This file is the deduplicated synthesis.

Many issues were independently rediscovered by multiple agents from different angles; those are merged below into one entry with all contributing findings cross-referenced.

## Critical

### [FIXED] C-1. Deploy script leaves the deployer EOA with permanent, unilateral `EXECUTE_PERMISSION` on the DAO
**Found by**: access-control (AC-1), governance (GOV-1), general (GEN-1) — independently confirmed by three passes.
**Location**: `script/InstallNFTVoting.s.sol:110-131`, `_buildPermissionActions` at `:188-209`, interacting with `DAOFactory.createDao` (`lib/osx/.../DAOFactory.sol:182-185`).

`createDaoAndInstall` creates the DAO with an **empty** plugin-settings array, which makes `DAOFactory` grant `EXECUTE_PERMISSION_ID` on the new DAO to `msg.sender` — the deployer EOA under `vm.startBroadcast`. The install script uses that permission once, to run its own `dao.execute(...)` permission-wiring batch, and **never revokes it**. No action anywhere in the script, the justfile, or the README's deployment/post-deployment checklists does so either.

Result: after a "successful," fully-installed NFT governance DAO, the deployer key can call `dao.execute()` directly — bypass every proposal, vote, quorum and threshold in the plugin — to drain the treasury, grant itself `ROOT_PERMISSION_ID`, mint itself unlimited voting NFTs, or rewrite voting settings. The README's own ceremony instructs operators to treat that key as a disposable burner (`cast wallet new`, then refund and discard it), while it in fact retains god-mode over the DAO forever. Compounded by the default `NFT_COUNT=1` minting 100% of initial voting power to that same deployer.

**Recommendation**: Add a `revoke(dao, deployer, EXECUTE_PERMISSION_ID)` action as the **last** step of the same install `dao.execute` batch (self-revocation mid-batch is safe — permission is checked once on entry), and assert post-install that `dao.isGranted(dao, deployer, EXECUTE_PERMISSION_ID, "") == false`. Add the same assertion to `test/fork/InstallNFTVoting.t.sol` and the README's post-deployment checklist.

**Resolution:** revocation logic added in the installation script.

## High

### [FIXED] H-1. Foundry broadcast splits `deployMinimalProxy` into two transactions — the NFTVoting clone is front-runnably uninitialized
**Found by**: proxies (PROXY-1).
**Location**: `script/InstallNFTVoting.s.sol:170-184`, via `ProxyLib.deployMinimalProxy` (`lib/osx-commons/.../ProxyLib.sol:34-42`).

`deployMinimalProxy` is an inlined `internal` library call, so its two steps — clone `CREATE` and `initialize()` `CALL` — surface as **two separate top-level transactions** under `forge script --broadcast` (empirically confirmed via broadcast artifact inspection and a passing PoC). The EIP-1167 clone therefore sits uninitialized on-chain between transactions. `NFTVoting.initialize()` is `external initializer` with no access control on caller or `_dao` argument, so a mempool-watching attacker can front-run the second transaction and become the plugin's permanent authority (their own DAO, their own voting token). The subsequent permission-grant transaction (`_dao.execute` granting the plugin `EXECUTE_PERMISSION_ID` on the real DAO) can still land afterward since Foundry doesn't wait for prior receipts by default, escalating to a real-DAO takeover path.

**Recommendation**: Wrap clone-deployment + `initialize()` in a single external call (e.g. a small `NFTVotingFactory.deploy(...)` helper contract) so both steps are nested sub-calls of one broadcast transaction, and `require(plugin.dao() == dao)` on-chain immediately after.

**Resolution**: A proxy factory is being used to deploy the contract. Clone and initialize happen on the same external call

### [FIXED] H-2. `_startDate` has no upper bound — proposals can be pinned to an arbitrarily stale census and executed as a time bomb
**Found by**: precision-math (MATH-1), governance (GOV-2), general (GEN-4).
**Prior audit**: `[FIXED]` **appears incomplete** — pashov Lead #4 flagged "`_validateProposalDates` has no `endDate` upper bound → permanently-pending proposals" and the team's resolution added the 365-day cap now in `Proposal.sol:398`. That cap is measured `startDate + 365 days`, so it bounds *duration*, not how far `startDate` itself can sit in the future — which is the mechanism this finding exploits. The original ticket can likely be reopened against this report rather than filed fresh.
**Location**: `Proposal._validateProposalDates()` (`src/base/Proposal.sol:366-404`).

The 365-day cap added in a recent fix bounds `endDate - startDate`, not `startDate - block.timestamp`. `_startDate = block.timestamp + N years` is accepted with no ceiling at all. Since `snapshotTimepoint`, `minVotingPower` and `minApprovalPower` are all frozen at *creation* time, a proposal created today with a vote scheduled years out is decided by today's census — using voting power of holders who may have since sold or been force-transferred out of every NFT — while current members (with zero snapshot power) cannot vote, oppose, or cancel it. Because `CREATE_PROPOSAL_PERMISSION_ID` is granted to `ANY_ADDR` by the install script, anyone can plant such a proposal; a coalition that ever held quorum can park an unlimited number of these as permanent, un-revocable time bombs.

**Recommendation**: Bound `startDate` to `block.timestamp + MAX_START_OFFSET` (e.g. 30 days), and apply the total-lifetime ceiling from `block.timestamp` (not just from `startDate`) on both the explicit- and default-`endDate` branches. Consider adding a cancel/veto path.

**Resolution**: added a check to prevent `startDate` from being later than a year. Even though this fixes the finding, the snapshot design could make a proposal un-voteable if the electoral census of the creation time is sustancially different than the future electoral.

## Medium

### [FIXED] M-1. `updateVotingToken` corrupts or permanently bricks every in-flight proposal
**Found by**: precision-math (MATH-2), governance (GOV-4), access-control (AC-2), ERC-721 (NFT-1), general (GEN-2), DoS (DOS-3) — the single most cross-confirmed finding in this audit, independently reproduced with passing PoCs by four separate agents.
**Prior audit**: **extends an open, unresolved prior finding** — pashov finding #6 (confidence 58, no `[FIXED]`/`[WONT-FIX]` tag, i.e. left as an accepted-but-unaddressed trusted-token assumption) already identified that `isSupportThresholdReachedEarly`'s subtraction can underflow "with a non-standard voting token," scoped to a token installed at `initialize` time. This audit shows the identical underflow — plus tally corruption and total vote lockout — is reachable with the **standard, in-scope `GovernanceERC721`** simply by calling the already-shipped `updateVotingToken` while a proposal is open; no non-standard/malicious token is required. That raises this from a "trusted external token" caveat to a reproducible bug in the plugin's own supported token-migration flow. Recommend treating this as the priority follow-up to pashov #6.
**Location**: `Settings.updateVotingToken()`/`_updateVotingToken()` (`src/base/Settings.sol:158-180`); consumed in `Votes._vote()`/`_canVote()` and `Proposal.isSupportThresholdReachedEarly()`.

Every proposal snapshots a `snapshotTimepoint`, but **not** the token it was measured against. `votingToken` (and the derived `tokenIndexedByTimestamp` clock-mode flag) is single, mutable, plugin-wide state. Swapping it — an intentional, DAO-only, otherwise-legitimate governance action — while proposals are open produces, depending on the specific swap: (a) an unconditional arithmetic-panic revert in `isSupportThresholdReachedEarly` that permanently bricks `canExecute`/`hasSucceeded`/`execute` for open EarlyExecution proposals; (b) total vote lockout (`_canVote` returns false for everyone) if the new token has no history at the old timepoint; (c) silent tally corruption in VoteReplacement mode, where a vote change is debited using the *new* token's power against a tally built from the *old* token's power, leaving phantom votes that can flip an outcome. All three were reproduced with compiling/passing Foundry PoCs.

**Recommendation**: Add `votingToken` (and ideally the resolved `tokenIndexedByTimestamp`) to `ProposalParameters`, pinned at `createProposal` time exactly like `snapshotTimepoint`, and read the pinned value everywhere voting power is resolved for a given proposal. Minimum viable mitigation if that's too invasive: forbid `updateVotingToken` while any proposal is open, and make the early-execution subtraction saturate instead of underflow-revert.

**Resolution:** proposal now snapshots the voting token to prevent in-flight proposal breaks

### [FIXED] M-2. `setTargetConfig` accepts a `DelegateCall` target that is not the DAO — a full plugin-storage takeover primitive
**Found by**: access-control (AC-3), governance (GOV-10, Info-rated but describing the same mechanism).
**Location**: `PluginCloneable._setTargetConfig()` (`lib/osx-commons/.../PluginCloneable.sol:105-118`); reachable via `NFTVoting.initialize()` and post-install via `SET_TARGET_CONFIG_PERMISSION_ID` (granted to the DAO).

The only guard blocks `target == the DAO itself` combined with `Operation.DelegateCall`; any *other* address with `DelegateCall` is accepted. `Proposal._execute` then `delegatecall`s into that target on every proposal execution — running arbitrary code **in the plugin's own storage context**, able to overwrite the DAO pointer (`dao_`), `votingToken`, `votingSettings`, or the entire `proposals` mapping. The install script (`script/InstallNFTVoting.s.sol:236-241`) reads `TARGET_ADDRESS`/`TARGET_OPERATION` straight from unvalidated env vars, so a single `.env` mistake (`TARGET_OPERATION=1` with a non-DAO address) compromises the plugin from block zero; it is also reachable post-install via one passing governance proposal, after which the backdoor controls the very permission checks that would be needed to remove it.

**Recommendation**: In the install script, `require(targetConfig.operation == Operation.Call)` unless a genuinely-audited delegatecall executor is intended; in the contract, consider overriding `_setTargetConfig` to reject `DelegateCall` outright unless the plugin explicitly needs it.

**Resolution**: Prevent delegate calls from the install script and the execute function. That way we guarantee that the plugin state (votingToken, proposal, etc) will stay safe if a malicious update changes the target contract to a malicious one that could execute code logic on top of the plugin contract state.

### [WONT-FIX] M-3. DAO holding `MINT`+`BURN`+`TRANSFER` on the voting token lets a bare majority permanently seize the electorate
**Found by**: access-control (AC-4).
**Location**: `GovernanceERC721.mint()/burn()/adminTransfer()` (`src/erc721/GovernanceERC721.sol:124-144`); grants in `script/InstallNFTVoting.s.sol:204-207`.

The access-control wiring itself is correct, but the composition is self-reinforcing: a proposal that passes on today's bare majority can mint itself an unbounded supermajority and/or burn every dissenter's NFT (auto-self-delegation makes new mints count from the next block), after which no future vote can ever dislodge the winner. No supply cap, no cooldown, no minority protection exists.

**Recommendation**: Do not grant all four token permissions to the same DAO-execution surface by default; consider not granting `TRANSFER_PERMISSION_ID` (forced transfer) in the standard install; add a mint supply cap.

**Resolution:** The electorate choosing is an off-chain process that it is not clear yet how it will be handled. Every citizen could create a proposal to join but that would require a vote per citizen. A trusted entity could have the transfer, mint, burn permissions to do it in a centralized manner.

### [FIXED] M-4. `createProposal` accepts more actions than the DAO's executor will ever run — `canExecute()` lies
**Found by**: DoS (DOS-1), backed by a passing PoC with measured gas costs.
**Location**: `Proposal.createProposal()` (`src/base/Proposal.sol:307-312`) vs. the DAO/Executor's hardcoded `MAX_ACTIONS = 256`.

The plugin never mirrors the executor's 256-action cap. A proposal with 257+ actions is accepted, voted on for the full period, and `canExecute()` reports `true` throughout — but `execute()` reverts `TooManyActions()` permanently. Confirmed cheap (≈13.25M gas for 257 trivial actions, well within one mainnet block, far cheaper on L2s) and reachable by anyone since proposal creation is `ANY_ADDR`.

**Recommendation**: Add `require(_actions.length <= 256)` (or the executor's exact constant) to `createProposal`.

**Resolution:** added the require statement in `createProposal`

### [FIXED] M-5. Permissionless `execute()` + discarded `allowFailureMap` lets any address consume a passed proposal with approved actions silently skipped
**Found by**: DoS (DOS-2), overlapping with governance's execution-timing finding (GOV-7).
**Location**: `Proposal.execute()`/`_execute()` (`src/base/Proposal.sol:41-64`).

Actions whose bit is set in `allowFailureMap` are allowed to fail without reverting the whole execution; the plugin discards the executor's returned failure bitmap entirely (not stored, not emitted). Combined with `EXECUTE_PROPOSAL_PERMISSION_ID` granted to `ANY_ADDR`, an attacker with zero stake can front-run the honest executor, flip state so an allowed-to-fail action fails (revoke an allowance, blocklist a recipient, break a swap's slippage), and call `execute()` themselves — the proposal is marked `executed = true` and `ProposalExecuted` fires as if everything succeeded, but the approved action never ran and can never be re-run. Confirmed with a passing PoC. More broadly (per GOV-7), the permissionless executor also gets unilateral choice of *which block* any price/state-sensitive action executes in — a pure MEV surface with no timelock to bound it.

**Recommendation**: Surface the failure bitmap (event or storage) instead of discarding it; do not grant `EXECUTE_PROPOSAL_PERMISSION_ID` to `ANY_ADDR` by default — restrict it to token holders or a keeper role.

**Resolution**: We are emitting the resulting failure map when a proposal is executed. Indexers and chain observers will be able to see the result of the actions and save that information for later.

### [FIXED] M-6. Quorum denominator counts undelegated tokens — permissionless `delegate(address(0))` quorum griefing
**Found by**: governance (GOV-5), ERC-721 (NFT-4) — both with passing PoCs.
**Location**: `Settings.totalVotingPower()` (`src/base/Settings.sol:63-71`); NatSpec is also factually wrong.

`totalVotingPower` (used as the quorum/approval denominator) is OZ's `getPastTotalSupply` — total minted-minus-burned, **regardless of delegation** — not "tokens that have been delegated" as the NatSpec claims. `delegate(address(0))` is permitted with no check. A coalition can call it from enough addresses to push reachable turnout below `minParticipation` of the (unchanged) total supply, permanently deadlocking every future proposal — cheaply, reversibly, and without transferring or burning anything.

**Recommendation**: Fix the NatSpec to state the real semantics and its implication for `minParticipation` headroom; consider rejecting `delegate(address(0))` in `GovernanceERC721` outright, since it has no legitimate purpose on a closed civic membership token and directly enables this griefing.

**Resolution:** NatSpec comment fixed. The total number of minted tokens is the total voting power. Each user needs to delegate his token (to himself or a third-party) in order to be able to submit a vote

### [FIXED] M-7. Governance can permanently brick itself via unbounded settings, with zero recovery path
**Found by**: governance (GOV-6), DoS (DOS-6).
**Prior audit**: `[FIXED]` **appears incomplete for the `minProposerVotingPower` half** — pashov finding #5 flagged this exact "no upper bound... permanently and irreversibly disables all proposal creation" scenario and marked it `[FIXED]`, with the resolution stating that `canCreateProposal`'s `if` condition "uses `minProposerVotingPower`... to determine if a user should be able to create the proposal." That describes the existing *lower-bound* enforcement, which was never in question — the current source (`Settings._updateVotingSettings`, verified in this pass) still has no upper-bound check on `minProposerVotingPower` at all, so the specific scenario pashov #5 described looks unresolved. The `minParticipation`/`minApprovals`-at-100% half of this finding is new, not covered by #5.
**Location**: `Settings._updateVotingSettings()` (`src/base/Settings.sol:116-153`).

`minProposerVotingPower` has no upper bound at all (settable above any holder's power, permanently blocking `createProposal` for everyone), and `minParticipation`/`minApprovals` may be set to 100% (mathematically unreachable the moment any single NFT is lost, stranded, or held by a non-voting contract). Since `UPDATE_VOTING_SETTINGS_PERMISSION_ID` is held only by the DAO, and the DAO can only act through a passing proposal via this same plugin, any of these is a one-transaction, irreversible bricking of governance.

**Recommendation**: Cap `minParticipation`/`minApprovals` below 100% (e.g. 90%); cap `minProposerVotingPower` against the live census at update time.

**Resolution**: `minParticipation` and `minApprovals` have been capped at 90% for practical scenarios. `supportThreshold` can still be 99% if in some cases we need the large majority of support for a certain proposal.

### [WONT-FIX] M-8. No execution delay + `ANY_ADDR` executor gives an arbitrary third party unilateral choice of execution block
**Found by**: governance (GOV-7), overlapping with DOS-2.
**Prior audit**: adjacent but distinct from pashov Lead #1 ("borrowed-majority governance: no voting delay + early execution inside `createProposal`"), which was about a same-transaction flash-loan-style takeover and was resolved by decoupling `createProposal` from voting (now requires ≥2 transactions). That fix closes the *flash-loan* angle; it does not address the separate, still-open concern here — an arbitrary, unstaked executor's freedom to choose *which block* an already-passed, multi-transaction proposal executes in, for MEV/sandwich purposes.
**Location**: `Proposal.execute()` (`src/base/Proposal.sol:41-46`); grant at `script/InstallNFTVoting.s.sol:200`.

Distinct from M-5's failure-skipping angle: even with `allowFailureMap == 0`, anyone can execute a passed proposal in any block they choose, with no minimum delay after `endDate`. For any proposal action whose outcome depends on external state (a DEX swap, a price-dependent purchase), the permissionless executor can bundle `execute()` with state manipulation (sandwich-style) to the DAO's detriment. (Early-execution *outcome* timing was checked and found not exploitable — `isSupportThresholdReachedEarly` is genuinely conclusive once true.)

**Recommendation**: Add a minimum delay between `endDate` and executability (e.g. 1 day), or restrict `EXECUTE_PROPOSAL_PERMISSION_ID` away from unconditional `ANY_ADDR`.

**Resolution:** We recognize the DeFi risks in no-delay execution but this DAO will mainly send funds to third-parties and might not be target of MEV sandwich attacks. We hope to address this in the future after showing production usage which will depend on showing that an approved proposal can be executed immediately without any condition.

### [WONT-FIX] M-9. Succeeded proposals never expire — unbounded execution window
**Found by**: governance (GOV-3).
**Location**: `Proposal._canExecute()`/`_hasSucceeded()` (`src/base/Proposal.sol:81-142`).

A proposal that reached its thresholds stays executable forever — there is no deadline after which a stale, already-approved action becomes un-executable. Combined with `ANY_ADDR` execution (M-8), an approved action can be held back and fired years later against conditions the electorate never evaluated.

**Recommendation**: Add an execution grace period after `endDate`, after which `_canExecute` returns `false`.

**Resolution:** The main premise of the DAO is that funds will be send regardless of the public sector willingness to do so. If that means that a proposal would not be executed in the short term, then the proposal should be executable until someone does it. We do not want stale proposals. The recipient has the economic incentive of executing the proposal any time he wants.

## Informational

- [WONT-FIX] **I-1. No storage gaps (`__gap`) in `Settings`/`Proposal`/`Votes`** — inert today (the plugin uses a non-upgradeable minimal-proxy clone, not UUPS), but would silently corrupt all deployed proposals' storage if the plugin is ever migrated to an upgradeable pattern (PROXY-3).
- **I-2. `_updateVotingToken`'s ERC-165 gate rejects a canonical, unmodified OpenZeppelin `ERC721Votes` token** (which doesn't self-report `IVotesUpgradeable`'s interface ID) while providing no real trust guarantee against a token that lies about supporting it (NFT-5).
- [WONT-FIX] **I-3. A DAO-installed malicious/pausable/blacklisting voting token fully controls vote accounting** — not independently exploitable (requires the same `UPDATE_VOTING_SETTINGS_PERMISSION_ID` that already controls the DAO), but worth an explicit trust-assumption note in the README (NFT-6).
- [FIXED] **I-4. Ratio-bound NatSpec/README documented intervals are narrower than the code's actual accepted range, and the `RatioOutOfBounds` revert on a zero value reports a misleading (upper-bound) limit** (MATH-6).
- **I-5. Unit tests deploy the plugin behind a UUPS/ERC-1967 proxy; production uses an EIP-1167 minimal proxy** — the two paths are inert-equivalent today but would silently diverge on a future change, and the unit suite never exercises H-1's actual deployment shape (GEN-8).
- **I-6. `abstract contract Proposal` shadows the inherited `INFTVoting.Proposal` struct name** — compiles correctly but is a readability/maintenance hazard (GEN-9).
- **I-7. `eip712Domain()` (ERC-5267) is implemented but not advertised via `supportsInterface`** — no security impact, minor interop friction for signature-relaying tooling (SIG-1).
- **I-8. No test coverage for the `delegateBySig`/EIP-712 signed-delegation path** — correct today by inspection of the pinned OZ 4.9.6 source, but unguarded against regression (SIG-3).
- **I-9/I-10. Confirmed SAFE, no action needed**: (a) `NFTVoting`'s un-cloned base implementation IS protected against direct `initialize()` by `PluginCloneable`'s constructor (`_disableInitializers()`), contrary to what an initial read might suggest (PROXY-4); (b) no UUPS surface, no CREATE2/metamorphic exposure, all OZ imports are correct upgradeable variants (PROXY-5).

## Cross-cutting observations

1. **The token-swap bug (M-1) is the highest-confidence finding in this audit** — reproduced independently, with compiling PoCs, by four of the eight specialist passes from four different angles (math, governance, NFT mechanics, DoS). Fix it first.
2. **The deployer-retains-EXECUTE-PERMISSION bug (C-1) is the highest-severity finding** — it makes every other governance protection in the codebase decorative until fixed, and is purely a deployment-script defect, not a contract defect.
3. **`ANY_ADDR` permission grants recur as a root cause or amplifier** across H-2, M-4, M-5, M-8, L-3 — none of them are individually mis-grants (verified against `PermissionManager`'s actual restriction list), but their cumulative effect is that almost every plugin entry point is reachable by an unaffiliated address, and several of the above findings only become cheap/practical because of that.
4. **Five previously-fixed bugs were re-verified complete** and are not re-reported: early-execution-before-`endDate` logic, initializer-disable-after-constructor ordering, the 365-day *duration* bound (though H-2 shows the *lifetime* bound is still open), `_msgSender()` in proposal-id computation, and clock detection for the two standard ERC-6372 modes (though L-9 shows non-standard clocks are still misclassified).
