# ERC-721 / Governance-NFT domain findings

Headline: 1 Medium (token swap corrupts open proposals — confirmed to flip a tally and to permanently brick a proposal), 3 Low, 2 Info.

---

## [NFT-1] Swapping the voting token corrupts or permanently bricks already-open proposals
**Severity**: Medium
**Category**: erc721
**Location**: Settings._updateVotingToken() (src/base/Settings.sol:164-180); consumed by Votes._vote() (src/base/Votes.sol:36) and Proposal.isSupportThresholdReachedEarly() (src/base/Proposal.sol:151-159)

**Description**: `ProposalParameters` (src/base/INFTVoting.sol:95-102) pins `snapshotTimepoint`, `votingMode`, `supportThreshold` and `minVotingPower` at creation time, but it does **not** pin the voting token, nor the clock unit (`tokenIndexedByTimestamp` is a single plugin-wide storage slot in `Settings`). `updateVotingToken` can be called at any time and immediately changes what every already-open proposal resolves `getPastVotes` / `getPastTotalSupply` against, while the tallies already accumulated under the *old* token stay in storage. Two distinct breakages follow:

1. **Cross-clock swap (block-number token -> timestamp token, or vice versa).** The stored `snapshotTimepoint` is a block number but is now fed to a timestamp-indexed token. It still passes OZ's `require(timepoint < clock())` (a block number is always far below a unix timestamp), so nothing reverts loudly — it silently resolves to a checkpoint from "the dawn of time", returning `0` for every voter and `0` for total supply. `isSupportThresholdReachedEarly` then computes `totalVotingPower(snapshot) - tally.yes - tally.abstain` = `0 - 5 - 0`, which reverts with a checked-arithmetic panic. `canExecute` / `hasSucceeded` revert forever, and `_canVote` returns false for everyone: the proposal is unexecutable and unvotable, permanently. The repo explicitly supports both clock modes (`test/mocks/MockTimestampClockToken.sol`, `Settings._detectTokenClock`), so this is a supported configuration, not a contrived one.
2. **Same-clock swap.** Balances differ between the old and new token, so `_vote`'s subtract-then-add replacement logic mixes units: it subtracts the *new* token's power from a tally that was built with the *old* token's power. This leaves phantom votes (or underflow-reverts a voter's ability to change their mind).

**Proof of Concept** (both confirmed passing):

`test_tokenSwapBricksOpenProposal` — Alice and Bob hold 5 NFTs each, EarlyExecution mode.
1. Alice creates proposal `pid` and votes Yes (tally.yes == 5).
2. While `pid` is still open, the DAO migrates to `MockTimestampClockToken` via `plugin.updateVotingToken(...)` — a routine, legitimate governance action.
3. `plugin.canExecute(pid)` now **reverts** (arithmetic underflow inside `isSupportThresholdReachedEarly`). `plugin.canVote(pid, BOB, No)` returns `false`. The proposal can never be executed and never be voted on again.

`test_tokenSwapUnderflowsVoteReplacement` — VoteReplacement mode, Alice holds 5 of the old token and 1 of a pre-existing second token.
1. Alice votes Yes -> `tally.yes == 5`.
2. DAO swaps to the second token (same block-number clock).
3. Alice changes her vote to No. `_vote` reads `votingPower = 1` from the new token, so it does `tally.yes -= 1` and `tally.no += 1`.
4. Final tally: **yes: 4, no: 1** — 4 "yes" votes remain from a voter who withdrew her support and is the only Yes voter. Support threshold now reads 4 vs 1 instead of 0 vs 1. Outcome flipped.

**Recommendation**: Snapshot the token (and its clock mode) per proposal, exactly as the timepoint already is:

```solidity
// INFTVoting.ProposalParameters
struct ProposalParameters {
    VotingMode votingMode;
    uint32 supportThreshold;
    uint64 startDate;
    uint64 endDate;
    uint64 snapshotTimepoint;
    uint256 minVotingPower;
    IVotesUpgradeable votingToken;   // <-- new
}
```
then read `proposal_.parameters.votingToken.getPastVotes(...)` in `Votes._vote`/`_canVote` and `proposal_.parameters.votingToken.getPastTotalSupply(...)` in `Proposal.isSupportThresholdReachedEarly` (pass the proposal's token into `totalVotingPower`).

If per-proposal snapshotting is considered too invasive, the minimum acceptable mitigation is to forbid the swap while proposals are live — e.g. track `openProposalCount` and `require(openProposalCount == 0, "open proposals")` in `_updateVotingToken` — and to defensively saturate the early-execution subtraction:

```solidity
uint256 total = totalVotingPower(proposal_.parameters.snapshotTimepoint);
uint256 counted = proposal_.tally.yes + proposal_.tally.abstain;
uint256 noVotesWorstCase = total > counted ? total - counted : 0;
```

## [NFT-2] Auto-self-delegation silently reverses a holder's deliberate opt-out; anyone can force it
**Severity**: Low
**Category**: erc721
**Location**: GovernanceERC721._afterTokenTransfer() (src/erc721/GovernanceERC721.sol:159-170)

**Description**: The specific concern of auto-delegation overriding an intentionally chosen delegate was checked and the guard `delegates(to) == address(0)` **does** correctly protect a normal third-party delegation: if Alice delegated to Carol, an incoming transfer routes the new unit to Carol and does not touch Alice's choice (confirmed by `test_explicitThirdPartyDelegationSurvives`). So the "resets my delegate" concern is **not** real for the common case.

There is exactly one preference the guard cannot distinguish: `address(0)` is simultaneously "never delegated" and "explicitly delegated to nobody". OZ 4.9's `VotesUpgradeable._delegate` has no zero-address check, so `delegate(address(0))` is a supported way for a holder to withdraw their voting weight (a custodian, escrow, bridge or treasury contract that must not carry governance power would plausibly do this). Any subsequent incoming token — which **any third party can push unilaterally**, no consent required — re-triggers `_delegate(to, to)` and restores the holder's *entire* balance to self-delegated voting power, not just the newly received unit.

**Proof of Concept** (`test_autoDelegationResetsOptOut`, passing):
1. Alice is minted 3 NFTs; auto-delegation sets `delegates(ALICE) == ALICE`, `getVotes(ALICE) == 3`.
2. Alice deliberately opts out: `token.delegate(address(0))` -> `getVotes(ALICE) == 0`.
3. Bob (or any holder, or the `TRANSFER_PERMISSION_ID` holder via `adminTransfer`, or the DAO via `mint`) sends Alice **one** NFT.
4. `delegates(ALICE) == ALICE` again and `getVotes(ALICE) == 4`. Alice's opt-out is gone and her full weight is back, without her signing anything.

Impact is bounded: it *grants* power to the recipient rather than taking it away, and `totalVotingPower` (total supply) is unchanged either way, so quorum math does not move. It is a forced-state-change / UX-surprise issue, not a vote-stealing one. Rated Low, not Medium.

**Recommendation**: Track the opt-out explicitly so `address(0)` is unambiguous, e.g.

```solidity
mapping(address => bool) private hasDelegated;

function _delegate(address account, address delegatee) internal virtual override {
    hasDelegated[account] = true;
    super._delegate(account, delegatee);
}

function _afterTokenTransfer(address from, address to, uint256 firstTokenId, uint256 batchSize)
    internal virtual override
{
    super._afterTokenTransfer(from, to, firstTokenId, batchSize);
    if (to != address(0) && !hasDelegated[to]) {
        _delegate(to, to);
    }
}
```
(Note the storage addition makes this a breaking layout change; since the contract is deployed with `new` rather than behind a proxy that is acceptable here.) At minimum, document in the NatSpec that `delegate(address(0))` is not a durable opt-out on this token.

## [NFT-3] `_mint`/`_transfer` without a receiver check can strand an NFT and its voting weight forever
**Severity**: Low
**Category**: erc721
**Location**: GovernanceERC721._mintTo() (src/erc721/GovernanceERC721.sol:149-154), GovernanceERC721.adminTransfer() (src/erc721/GovernanceERC721.sol:141-144)

**Description**: `_mintTo` uses `_mint` and `adminTransfer` uses `_transfer`, both of which skip `_checkOnERC721Received`. Assessing the trade-off directly:

*The reentrancy side is genuinely safer and nothing is lost by it.* Even if `_safeMint` / `_safeTransfer` were used, the `onERC721Received` callback fires **after** `_afterTokenTransfer` has already moved the voting units and pushed checkpoints, and every read path in the plugin (`Votes._vote`, `Votes._canVote`, `Proposal.canCreateProposal`, `Proposal.isSupportThresholdReachedEarly`) resolves against a **strictly past** timepoint (`block.number - 1` / the stored `snapshotTimepoint`). A reentering receiver therefore cannot make freshly-minted or freshly-received units count in any proposal. There is no double-counting vector here. Note also that holders can still call the inherited `safeTransferFrom`, so the callback surface exists regardless — avoiding it in the two admin paths buys no additional safety.

*The other side is a real, if operator-triggered, problem.* Because the check is skipped, `mint()` and `adminTransfer()` succeed against a contract that cannot handle ERC-721. The NFT is then unrecoverable by its "holder", and — because `_afterTokenTransfer` auto-self-delegates it — the unit is counted in both `getPastVotes(stuckContract)` and `getPastTotalSupply()`, i.e. it permanently inflates the `minVotingPower` / `minApprovalPower` denominators (`Proposal.createProposal` lines 296-298) with power that can never be cast. Enough stranded tokens make `isMinParticipationReached` / `isMinApprovalReached` unreachable and governance deadlocks.

**Proof of Concept** (`test_mintToNonReceiverContractSucceeds`, passing):
1. Deploy `contract Dumb {}` — no `onERC721Received`, no way to move an NFT out.
2. `token.mint(address(dumb))` **succeeds** (with `_safeMint` it would revert with "ERC721: transfer to non ERC721Receiver implementer").
3. At the next block: `totalVotingPower == 2` while only 1 unit is castable; `getPastVotes(dumb) == 1`, forever, and `Dumb` can never vote or transfer.

Rated Low rather than Medium because both entry points are permissioned (`MINT_PERMISSION_ID`, `TRANSFER_PERMISSION_ID`) and the damage is recoverable: `BURN_PERMISSION_ID` can burn the stranded token, and burning does correctly decrement the total-supply checkpoint (verified in `test_burnAndAdminTransferSanity`).

**Recommendation**: Restore the receiver check on both admin paths — the reentrancy the check introduces is already provably harmless here, and it converts a silent permanent loss into a revert:

```solidity
function _mintTo(address _to) internal virtual returns (uint256 tokenId) {
    unchecked { tokenId = ++nextTokenId; }
    _safeMint(_to, tokenId);
}

function adminTransfer(address _from, address _to, uint256 _tokenId)
    external virtual auth(TRANSFER_PERMISSION_ID)
{
    _safeTransfer(_from, _to, _tokenId, "");
    emit AdminTransfer({from: _from, to: _to, tokenId: _tokenId});
}
```
If a deliberate escape hatch is wanted for recipients that are known-good non-receivers, add an explicit `mintUnsafe` / `adminTransferUnsafe` variant rather than making the unchecked path the default.

## [NFT-4] `totalVotingPower()` returns total token supply, not delegated voting power — NatSpec is wrong
**Severity**: Low
**Category**: erc721
**Location**: Settings.totalVotingPower() (src/base/Settings.sol:63-71)

**Description**: The NatSpec states: *"For an ERC-721 `Votes` token this equals the number of tokens that have been delegated (and are therefore authorized to vote) at `_timePoint`"*. That is not what OZ 4.9 does. `VotesUpgradeable._transferVotingUnits` pushes to `_totalCheckpoints` on mint/burn **unconditionally**, independent of delegation; OZ's own doc comment on `getPastTotalSupply` says "Votes that have not been delegated are still part of total supply, even though they would not participate in a vote." So `totalVotingPower` is total circulating supply.

Auto-self-delegation usually makes the two coincide, which is presumably why the comment was written — but the equality breaks whenever a holder calls `delegate(address(0))` (see NFT-2) or whenever tokens are stranded in a non-participating contract (see NFT-3). In those cases the `minVotingPower` and `minApprovalPower` denominators computed in `createProposal` exceed the power that can actually be cast, making quorum and min-approval harder (or impossible) to reach.

**Proof of Concept** (`test_totalVotingPowerCountsNonVotableTokens`, passing): Alice and Bob hold 5 NFTs each. Alice calls `delegate(address(0))`. At the next block: `plugin.totalVotingPower(tp) == 10`, but `getPastVotes(ALICE, tp) == 0` and `getPastVotes(BOB, tp) == 5` — only 5 of the 10 units in the denominator are castable. With `minParticipation` above 50%, no proposal can ever reach quorum.

Note this is *not* worse than simply abstaining from a security standpoint (a non-voter and an opted-out holder both fail to contribute participation), which is why it is Low and not Medium. The concrete defect is the incorrect NatSpec, which invites downstream integrators and future maintainers to reason about the denominator wrongly.

**Recommendation**: Fix the comment to match reality, and reference OZ's semantics:

```solidity
/// @notice Returns the total voting-unit supply checkpointed at a timestamp or block number.
/// @dev This is the total number of tokens in existence at `_timePoint` (each ERC-721 token is one
///     voting unit), NOT the number of tokens whose power has been delegated. Units held by an
///     account that has delegated to `address(0)`, or stranded in a contract that cannot vote, are
///     still counted here and therefore still raise the `minParticipation` / `minApproval`
///     denominators. See OpenZeppelin `Votes.getPastTotalSupply`.
```
Separately, consider whether `minParticipation` should be measured against castable power; if so it requires the token to expose a delegated-supply checkpoint, which OZ does not.

## [NFT-5] `_updateVotingToken`'s ERC-165 gate rejects canonical OZ `ERC721Votes` tokens and trusts self-reporting
**Severity**: Info
**Category**: erc721
**Location**: Settings._updateVotingToken() (src/base/Settings.sol:164-180)

**Description**: The gate requires `supportsInterface(type(IVotesUpgradeable).interfaceId)`. Stock OpenZeppelin `ERC721VotesUpgradeable` does **not** advertise that interface ID — only this repo's `GovernanceERC721` does, via the hand-rolled `supportsInterface` override (src/erc721/GovernanceERC721.sol:108-119). So a DAO wanting to migrate to an otherwise perfectly valid off-the-shelf OZ `ERC721Votes` token cannot: the call reverts with "token is not a Votes Upgradeable". Conversely the gate is purely self-reported and provides no real assurance — any contract can return `true` from `supportsInterface` while `getPastVotes` returns arbitrary values. It is a typo-guard, not a security control, which is the right framing but is not documented as such.

**Proof of Concept**: Scenario, not an exploit. `test/mocks/MockPlainERC721.sol` already covers the rejection path; the inverse (a stock OZ `ERC721Votes`) would be rejected too.

**Recommendation**: Either relax the second check to a behavioural probe, or document the constraint:

```solidity
try IVotesUpgradeable(address(_token)).getPastTotalSupply(block.number - 1) returns (uint256) {
    // ok
} catch {
    revert("token is not Votes-compatible");
}
```
and add to the NatSpec: *"This check is a misconfiguration guard, not a trust boundary: the token is fully trusted for vote accounting once installed."*

## [NFT-6] A pluggable malicious / pausable / blacklisting voting token fully controls vote accounting
**Severity**: Info
**Category**: erc721
**Location**: Settings.updateVotingToken() (src/base/Settings.sol:158-160), Votes._vote() (src/base/Votes.sol:35-36)

**Description**: Installing a hostile token is **not** a standalone vulnerability, because `updateVotingToken` is gated by `UPDATE_VOTING_SETTINGS_PERMISSION_ID`, which in a normal deployment is held by the DAO and can only be exercised by a passed proposal. An actor able to pass that proposal already controls the DAO and does not need a hostile token to get what they want. It is therefore Info, documented as a trust assumption — with the important caveat that the *unprivileged* consequence of a **benign** swap is a separate, real finding (NFT-1).

For completeness, the behaviours a hostile/quirky token would produce:
- Lying `getPastVotes` / `getPastTotalSupply`: arbitrary tallies and arbitrary quorum denominators. Nothing in `Proposal`/`Votes` cross-checks them; `isSupportThresholdReachedEarly` will checked-underflow-revert if `getPastTotalSupply < yes + abstain`, turning a lie into a DoS.
- Pausable / blacklisting: `getPastVotes` reverting makes `_canVote` and therefore `vote()` revert for the targeted account — selective disenfranchisement with no fallback path.
- Reentrancy on the `getPastVotes` read: the in-code comment at src/base/Votes.sol:35 flags this. The ordering is actually safe for the same-account case — `VoteOption state = proposal_.voters[_voter]` is read *after* the external call (line 37), so a nested `vote()` that records a vote is correctly observed and subtracted by the outer frame, with no double-count. This only degrades if the token returns *different* values across the nested calls, at which point the token is malicious by assumption.

**Proof of Concept**: Requires `UPDATE_VOTING_SETTINGS_PERMISSION_ID`; no unprivileged path exists.

**Recommendation**: No code change required for the privileged case. Document the trust assumption on `updateVotingToken` ("the voting token is fully trusted for all vote accounting; installing an untrusted token compromises every proposal"), and adopt the saturating subtraction from NFT-1 in `isSupportThresholdReachedEarly` so a misbehaving or mismatched token degrades to a wrong-but-live result instead of a permanently reverting one.

# Checklist coverage (items reviewed with no finding)

- **Large / encoded / non-sequential token IDs.** `_mintTo` assigns `++nextTokenId` (starts at 1); `unchecked` is safe. Confirmed by inspection that `NFTVoting.sol`, `base/Votes.sol`, `base/Proposal.sol` and `base/Settings.sol` never reference a token ID — all accounting goes through `getPastVotes` / `getPastTotalSupply` / `balanceOf`. Nothing depends on ID density or ordering. No finding.
- **Reentrancy via `onERC721Received`.** Analysed in full under NFT-3. The admin paths have no callback; the inherited `safeTransferFrom` does, but the callback fires after checkpoints are written and every plugin read is against a strictly past timepoint, so no double-count is reachable. `_afterTokenTransfer`'s `_delegate(to, to)` is also callback-free (it only emits events). Separately verified the delegation math cannot double-count: when `delegates(to)==0` the `super` call routes the unit to nobody and the following `_delegate` adds `balanceOf(to)` (already post-transfer) exactly once, including the case where `to` is already a delegatee for third parties. No finding beyond NFT-3.
- **Upgradeable / pausable / blacklist token plugged in.** Covered by NFT-1 (real) and NFT-6 (Info).
- **Constructor/initializer mints emitting events.** `initialize` loops `_mintTo` -> OZ `_mint`, which emits `Transfer(address(0), to, tokenId)`; the subsequent `_delegate(to, to)` emits `DelegateChanged` and `DelegateVotesChanged`. Indexers see everything. No finding.
- **`adminTransfer(_from, ...)` taking `_from` as a parameter.** Verified OZ `_transfer` enforces `require(ERC721.ownerOf(tokenId) == from, "ERC721: transfer from incorrect owner")` and `to != address(0)` — so a wrong `_from` reverts rather than silently reassigning, and `adminTransfer` cannot be used to burn. Confirmed live in `test_burnAndAdminTransferSanity` (reverts with the expected string). No approval-based theft vector: the function is permissioned and deliberately bypasses approvals, which is its documented purpose. No finding.
- **Holder-initiated transfers resetting a chosen delegate.** Tested and **disproven** for the normal case (`test_explicitThirdPartyDelegationSurvives`): an explicit delegation to a third party survives incoming transfers untouched. Only the `address(0)` ambiguity is affected — reported as NFT-2 at Low. Mid-proposal accounting is unaffected either way, since all vote reads use the stored past `snapshotTimepoint`.
- **Burn reducing past total supply.** Verified: `_burn` -> `_afterTokenTransfer(owner, 0, id, 1)` -> `_transferVotingUnits(owner, address(0), 1)` decrements `_totalCheckpoints`, and the override's `to != address(0)` guard correctly skips self-delegation on burn. Live check in `test_burnAndAdminTransferSanity`: `totalVotingPower` goes 4 -> 3 after one burn and the burned holder's `getPastVotes` drops accordingly. No drift. No finding.
- **Mint + auto-delegation vs. the `current - 1` snapshot.** Verified there is no off-by-one. Both the total-supply checkpoint (pushed by `super._afterTokenTransfer`) and the delegate checkpoint (pushed by `_delegate`) land at the same `clock()` key in the same block; OZ `Checkpoints.push` overwrites a same-key entry so the block's end-state is consistent. `getPastVotes` / `getPastTotalSupply` enforce `timepoint < clock()`, and `canCreateProposal` / `createProposal` use `block.number - 1`, so a token minted in block N is usable only from block N+1 onward — the intended backrun protection, working correctly. `GovernanceERC721` does not override `clock()`, so `Settings._detectTokenClock` correctly resolves `tokenIndexedByTimestamp == false`. No finding.
- **ERC-1155 dual-standard / CryptoPunks-style non-standard transfers / fractionalization.** Not applicable — single standard ERC-721, standard OZ transfer surface, no fractional or wrapped representation anywhere in `src/`.

Cross-domain note: `Proposal._proposalExists` treats `snapshotTimepoint == 0` as "does not exist", while `createProposal` computes `snapshotTimepoint = block.number - 1` under `unchecked`. At block 1 that yields 0 and at block 0 it underflows. Genesis-only, not an ERC-721 issue — also independently caught by the precision-math pass as MATH-4.
